Question 7

The GDPR constraint maps to the regional deployment lever (EU data zones): every Azure AI resource, search index and storage account that touches patient data must be created in an EU region such as France Central, Germany West Central or West Europe, and any Azure OpenAI model must use a Regional or Data Zone (EU) deployment type, never a Global deployment type, which can process requests in any Azure region worldwide. Four workflows are affected at the infrastructure level: Workflow A needs Azure AI Document Intelligence and the storage holding the scanned forms in an EU region, writing to an EU-hosted Dataverse environment, because each form carries name, date of birth, insurance ID and presenting complaint; Workflow C needs the script-generation model on an EU-region or Data Zone (EU) deployment and Azure AI Speech Text-to-Speech in an EU region, because each script combines appointment data and preferred language from Dataverse; Workflow D needs the claim-routing model on EU-only provisioned capacity, because claim emails contain patient and insurance details; and Workflow E needs the scheduled validation job, the CSV export and the exceptions report kept in an EU region (with any future model processing on Data Zone Batch (EU), not Global Batch), because all 2,100 weekly records are patient encounters. Workflow B is the only workflow not affected, because the 740 SharePoint PDFs are operational policies (infection control protocols, referral procedures, equipment maintenance schedules) and contain no patient data. Recommendation: still deploy Workflow B in the same EU region so the small IT team manages a single EU footprint, and instruct staff not to type patient details into policy questions, since that would bring Workflow B into scope.


Question 8

The two-second SLA maps to the Provisioned Throughput Units (PTU) capacity tier, because Workflow D is a real-time, synchronous, latency-sensitive workload where staff wait at their screen for each of the 800 daily routing decisions, and PTU reserves dedicated model capacity that gives consistent, predictable latency. The alternative consumption (pay-per-use/standard) tier is architecturally inappropriate because it runs on shared capacity whose latency is variable and can spike under load, with requests throttled when rate limits are reached, so it cannot guarantee a two-second response when all 14 clinics are submitting claims at peak hours (and batch processing is ruled out entirely, because it is asynchronous and returns results hours later). If the wrong tier were selected, staff would be left waiting several seconds or more for some routing decisions, or would see failed requests that need retrying, so they would go back to reading and forwarding claim emails manually, which defeats the purpose of automating Workflow D and erodes trust in the tool. Recommendation: deploy Workflow D's routing model on PTU, sized for peak-hour claim volume and placed in an EU data zone for GDPR, and treat the fixed monthly PTU cost as the price of meeting the SLA.
