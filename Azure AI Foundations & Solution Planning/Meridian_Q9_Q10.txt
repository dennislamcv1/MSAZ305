Question 9

Token Sizing Equation:
Monthly cost = (volume per day x days per month) x ((input tokens x input rate per token) + (output tokens x output rate per token))

Inputs for Workflow D:
- Monthly volume: 800 emails per day x 30 days = 24,000 classification requests per month
- Per request: 300 input tokens, 20 output tokens
- No vector search index is required, so token cost is the only cost in this model

Scenario 1: Frontier tier ($2.50 per 1M input tokens, $10.00 per 1M output tokens)

Step 1 - Convert rates to per-token:
  Input rate:  $2.50 / 1,000,000  = $0.0000025 per token
  Output rate: $10.00 / 1,000,000 = $0.00001 per token

Step 2 - Cost per request:
  Input:  300 x $0.0000025 = $0.00075
  Output: 20 x $0.00001    = $0.00020
  Total per request: $0.00075 + $0.00020 = $0.00095

Step 3 - Monthly cost:
  24,000 x $0.00095 = $22.80

Cross-check using monthly token totals:
  Input:  24,000 x 300 = 7,200,000 tokens (7.2M) x $2.50 per 1M  = $18.00
  Output: 24,000 x 20  = 480,000 tokens (0.48M) x $10.00 per 1M = $4.80
  Total: $18.00 + $4.80 = $22.80

Scenario 1 result: $22.80 per month ($273.60 per year)

Scenario 2: Lightweight tier ($0.15 per 1M input tokens, $0.60 per 1M output tokens)

Step 1 - Convert rates to per-token:
  Input rate:  $0.15 / 1,000,000 = $0.00000015 per token
  Output rate: $0.60 / 1,000,000 = $0.0000006 per token

Step 2 - Cost per request:
  Input:  300 x $0.00000015 = $0.000045
  Output: 20 x $0.0000006   = $0.000012
  Total per request: $0.000045 + $0.000012 = $0.000057

Step 3 - Monthly cost:
  24,000 x $0.000057 = $1.368, rounded to $1.37

Cross-check using monthly token totals:
  Input:  7.2M tokens x $0.15 per 1M  = $1.08
  Output: 0.48M tokens x $0.60 per 1M = $0.288
  Total: $1.08 + $0.288 = $1.368, rounded to $1.37

Scenario 2 result: $1.37 per month ($16.42 per year)

Comparison:
  Monthly saving: $22.80 - $1.368 = $21.432, rounded to $21.43 per month ($257.18 per year)
  Cost reduction: $21.432 / $22.80 = 0.94, a 94% reduction (the Frontier tier costs about 16.7 times more)

Architectural justification: The Lightweight tier is architecturally appropriate because Workflow D is a single-step classification of a short claim email into one of six fixed queues, returning a 20-token queue label with no multi-step reasoning, content generation or vector search, so a Frontier model's extra reasoning capacity would add about 16.7 times the cost without improving routing accuracy, while a smaller model also responds faster in support of the two-second SLA.


Question 10

Batch processing is not appropriate for Workflow D, and the constraint that rules it out is the two-second response SLA: clinic staff wait at their screen for each routing decision, while batch processing groups requests and returns results asynchronously, often hours later, so every one of the 800 daily claims would miss the SLA. The financial case is also weak, because 50% of the right-sized Lightweight cost of $1.37 per month saves only about $0.68 per month, against the cost of staff time lost while claims sit unrouted and the risk of delaying emergency claims. Batch processing belongs to workloads with no real-time SLA, such as Workflow E, whose results are not reviewed until two days after processing. Recommendation: reject the suggestion and keep Workflow D on synchronous, real-time inference with the Lightweight model, relying on right-sizing (already a 94% saving) rather than batching as the cost lever.
